# Стенд фронта

`sudo stand` собирает epus/frontend из ветки и поднимает его на
`https://<имя>.stand.yakutov.com`. API — dev (`api-lk.ldsn.dev`) или stage, стенд открыт
без входа. Docker напрямую недоступен — только эта команда.

## Поднять

```bash
git push origin <ветка>                        # стенд берёт ветку из git01
sudo stand up <ключ-задачи> --ref <ветка>      # напр. stt-12 --ref feature/task-123/foo
sudo stand wait <ключ-задачи>                  # до 15 мин; код 0 = стенд работает
```

- Имя стенда = ключ задачи multica в нижнем регистре (`stt-12`): стенд удалится
  сам, когда задачу закроют. Иначе живёт 48 часов с последнего `up`.
- Незапушенная работа: `--path <абсолютный путь к рабочей копии>` вместо `--ref`.
- Бэк stage вместо dev: `--env stage` (просят «со стейджем», «на стейдж-API»).
  Бэк запекается в сборку: сменить `--env` = `up` заново.
- Другой сайт: `--site <id>` (по умолчанию `azgaz`; есть `kz`, `agat`,
  `autoretail`, `dvaris`, `publisher`, `rusbus`).
- Повторный `up` с тем же именем пересобирает стенд на месте, адрес тот же.
- Сборки идут по одной; `wait` может сначала стоять в очереди. Вызов `wait`
  держи с таймаутом Bash не меньше 10 минут либо повторяй его.

## Проверить

Playwright MCP: открыть `https://<имя>.stand.yakutov.com`, пройти изменённый
сценарий, снять скриншот. Консоль — через `browser_console_messages`.

## Если упало

```bash
sudo stand status <имя>       # статус, причина, хвост лога сборки
sudo stand logs <имя> 200     # логи работающего стенда (SSR-ошибки) или сборки
```

Сборка упала на коде ветки (типы, импорты) — чинить в ветке и `up` снова.
Упала на окружении (сеть, git01, «нет свободных портов», «уже 8 стендов») —
это не твоя задача: опиши в отчёте и упомяни автора задачи.

## Отчёт

В комментарий задачи: ссылку на стенд, ветку и коммит, что проверено и
скриншот. Стенд больше не нужен — `sudo stand down <имя>`.

`sudo stand list` — все стенды: не удаляй чужие.
