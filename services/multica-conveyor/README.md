# multica-conveyor

Исходники сторожа конвейера: `multica-conveyor` и общий модуль `control_state.py`.

## Что это

Один файл (stdlib, Python 3.12) с двумя полосами, каждая со своим run-lock:

- **epics** — запуск приёмки отдельными задачами `atd` и слияние по их итогу, назначение следующей стадии, страница
  статуса. Запускает `multica-conveyor.timer` раз в 2 минуты; тик не ждёт проверку.
- **providers** — смена модели агента на лимите и единственный повтор после лимита. `multica-provider.timer` раз в минуту,
  `multica-conveyor --providers-only`. Таймер поставляется выключенным и включается по `--capabilities`.

`multica-conveyor --capabilities` печатает JSON `{"features": [...], "lanes": ["epics", "providers"], "schema": 1}`
и не читает конфиг.

`control_state.py` импортируют сторож, пульт `/opt/multica-control` и `subs-pick` (его зовёт старт каждого рана
claude/codex-reserve), поэтому на сервере три копии одного файла.

## Инфраструктурные повторы

Последний ран задачи активной стадии, упавший при старте CLI, восстановлении daemon или на сетевой инфраструктуре,
повторяется после `infra_retry_minutes` (по умолчанию `quota_retry_minutes`, затем 20 минут).
`infra_retry_limit` ограничивает число повторов подряд (по умолчанию 3; 0 запрещает повторы).
Активный ран блокирует повтор и сохраняет счётчик; другой завершённый исход сбрасывает его. Достижение лимита
однократно попадает в журнал и требует разбора.
Перед `issue rerun` состояние задачи и раны перечитываются под общим lock с полосой провайдеров; закрытая задача,
сдача на проверку, пауза и dry-run исключают запись.

## Повтор после лимита провайдера

Владелец один — полоса провайдеров; полоса эпиков после лимита ничего не повторяет. Каждый упавший на лимите ран
агента попадает в учёт (`_providers.<агент>.quota_pending` в state.json) и повторяется ровно один раз, когда профиль
агента снова можно брать: после переезда, возврата на основной или будильника сброса, но не в остывающий runtime,
не в ручном режиме и не пока вся цепочка ждёт сброса. Повтор привязан к поручению упавшего рана, а не к статусу
задачи (`quota_retry_plan`):

| ситуация | действие |
|---|---|
| по задаче идёт или ждёт ран | ждать, решить на следующем проходе |
| у агента в задаче был более поздний ран; поручение (комментарий или будильник) обработал другой ран; задача закрыта | не повторять |
| поручение исполнителя задачи или лидера её сквада, задача не на сдаче | `issue rerun` |
| упоминание в чужой задаче; новое поручение в задаче на сдаче | будильник именно этому агенту через минуту, ответ — в тред поручения |

Учёт начинается с момента включения (`quota_since`): более ранние падения задним числом не повторяются.
Запись в учёте живёт 7 дней. Сбой вызова Multica оставляет ран в учёте до следующего прохода.

Общий `control_state.py` также содержит `accounts`/`account_card`: пульт группирует несколько ключей с общей
строкой квоты одного провайдера в карточку аккаунта. Это представление не изменяет подписки и их лимиты,
которые использует `subs-pick`.

## Приёмка

Принимается любая подзадача эпика — с этапом или без — в `in_review` или в «Готово», если её коммит ещё не в `base`.
Что принимать, берётся только из метаданных задачи: `branch` и `commit` (полный SHA из 40 символов), их ставит
исполнитель при сдаче (`multica issue metadata set`). Ветка должна указывать ровно на этот коммит. Нет метаданных,
короткий SHA, коммита или ветки нет, ветка ушла дальше — приёмки нет, причина один раз пишется в журнал и видна на
странице у задачи. Комментарии задачи не читаются. Назначение по этапам от этого не зависит.

Проверка идёт отдельной задачей `atd` (`multica-conveyor --accept-job <файл>`), тик её не ждёт. Юнит сторожа —
oneshot: при выходе systemd убивает его потомков, а задача `atd` живёт вне юнита и переживает перезапуск и выкладку
сторожа. Файл задачи — `~/.local/state/multica-conveyor/accept-jobs/<задача>-<sha12>-<base12>.json`: одна пара
«коммит задачи + коммит base» — одна проверка, повтор тика и перезапуск сторожа её не дублируют, новый коммит любой
стороны — новая проверка. Воркер держит flock на `<файл>.lock`; незавершённая задача со свободным замком значит, что
воркер пропал (перезагрузка, OOM), — тик перезапускает её до 3 раз, затем это провал. На эпик — одна проверка за раз:
слияние сдвигает `base` остальным.

Воркер: клон коммита, поверх — зафиксированный коммит `base`, проверка диффа, команды `acceptance`. Итог пишет в файл
задачи, побочные действия делает тик: зелёно — вливает в `base` ровно проверенный коммит и ставит «Готово»; красно —
один комментарий лидеру с хвостом лога, задача в `in_progress`.

Ожидание общего ресурса: код из `acceptance_busy_codes` (по умолчанию 75 — так test-lock проверяемого репозитория
отвечает, не дождавшись замка) — команда повторяется через `acceptance_wait_poll` с, ожидание не входит в
`acceptance_timeout`. По умолчанию команды получают `E2E_LOCK_WAIT=0`, чтобы не ждать замок внутри своего таймаута.
Дольше `acceptance_wait_max` — приёмка отложена (не провал, без комментария и смены статуса) и через
`acceptance_retry_minutes` повторяется той же задачей.

В конфиге эпика:

| ключ | смысл |
|---|---|
| `acceptance` | команды, по очереди, `shell=True` в клоне |
| `acceptance_timeout` | секунд на каждую попытку команды (1500), без ожидания ресурса |
| `acceptance_path` | `PATH` для команд; без него — как у юнита |
| `acceptance_env` | дополнительные переменные; значения вырезаются из лога дословно |
| `acceptance_busy_codes` | коды «ресурс занят» (`[75]`) |
| `acceptance_wait_poll` / `acceptance_wait_max` | пауза между попытками (60 с) и предел ожидания (7200 с) |
| `acceptance_retry_minutes` | через сколько повторить отложенную приёмку (10) |

Полный лог (с редакцией токенов, права 0600) — `~/.local/state/multica-conveyor/accept/<задача>-<sha12>.log`,
старше 30 дней удаляется вместе со старыми файлами задач. В заголовке лога: ветка, коммиты, `PATH` и имена переменных.
По таймауту группе процессов команды шлётся TERM, через 5 с — KILL. Вывод самого воркера — `<файл задачи>.out`.

Что смотреть при сбое: файл задачи (`status`, `reason`, `code`, `log`), `atq`, `<файл>.out`, журнал на странице.
Остановить проверку: `kill` процесса из поля `pid` файла задачи — тик увидит пропавшего воркера и перезапустит её;
чтобы не перезапускал, задачу снимают со сдачи или меняют `commit` в метаданных.

## Состояние

`~/.local/state/multica-conveyor/{state.json,providers-status.json,status/,accept/,accept-jobs/}`, управление — `controls.json`
пульта. Конфиг — `/etc/multica-conveyor.json`.

## Проверка

    python3 -I -m unittest discover -s tests -q

Тесты изолированы: Multica подменена, git — во временных каталогах, реальные агенты не запускаются.
Холостой прогон по боевому конфигу: `MULTICA_CONVEYOR_STATE=<копия state.json> multica-conveyor --dry-run`.

## Выкатка

Не руками: через `harness-control` (`services/harness-control`), компонент `multica-conveyor`. Он кладёт
`multica-conveyor` в `/usr/local/bin` и `control_state.py` в `/usr/local/bin` и `/opt/multica-control`, перезапускает
таймеры и проверяет следующий плановый тик. `systemd/` — копия юнитов на сервере; сами юниты ставит оператор.
Задачи приёмки, идущие в `atd`, выкатка не прерывает: уже запущенный воркер дорабатывает на прежней версии файла.
Откат: `harness-control rollback multica-conveyor`; незавершённые файлы задач прежняя версия не читает — после отката
их можно удалить из `accept-jobs/`.
