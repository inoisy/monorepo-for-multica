# Стенд

Стенды поднимаешь сам, инструментами MCP `stand` — человека для этого не
зовёшь, даже если в задаче написано «попроси поднять стенд». Docker и sudo
напрямую не нужны.

Стенд — `https://<имя>.stand.yakutov.com`, открыт без входа. По умолчанию
собирается epus/frontend, API — dev (`api-lk.ldsn.dev`) или stage.

## Поднять

1. Запушь ветку в git01 — стенд берёт её оттуда.
2. `stand_up`: `name` = ключ задачи multica в нижнем регистре (`stt-12`),
   `ref` = ветка. Возвращается сразу, сборка идёт в фоне.
3. `stand_wait` с `name` — повторяй, пока ответ `BUILDING`. `READY` — стенд
   работает, `FAILED` — смотри хвост лога в ответе.

- Имя = ключ задачи: стенд удалится сам, когда задачу закроют. Иначе живёт
  48 часов с последнего `stand_up`.
- Незапушенная работа: `path` (абсолютный путь к рабочей копии) вместо `ref`.
- Бэк stage вместо dev: `env: stage` («со стейджем», «на стейдж-API»). Бэк
  запекается в сборку: сменить `env` = `stand_up` заново.
- Другой сайт: `site` (по умолчанию `azgaz`; есть `kz`, `agat`,
  `autoretail`, `dvaris`, `publisher`, `rusbus`).
- Повторный `stand_up` с тем же `name` пересобирает стенд на том же адресе.
- `follow: true` (только с `ref` на ветку) — стенд сам пересобирается на
  каждый новый коммит в ветке, проверка раз в 2 минуты. Повторный
  `stand_up` без `follow` слежение снимает.
- Сборки идут по одной: `stand_wait` может сначала стоять в очереди.
- Уже есть стенд из того же коммита (`stand_list`) — используй его.

## Не epus/frontend

`kind`: `node` (install по lock-файлу, `build`, `npm start`, слушать `PORT`),
`static` (каталог `publish`), `docker` (Dockerfile из ветки, `app_port`),
`compose` (docker-compose из ветки — см. ниже).
`repo` — алиас из `stand_repos`, `subdir` — подкаталог монорепо, `secrets` —
наборы переменных оттуда же. `ttl_hours` — срок жизни (48 по умолчанию,
до 168).

## Сервис с БД: kind compose

То же, что `docker compose up` на чистой машине, но на стенде.

- `stand_up` с `kind: compose`, `repo`, `ref`. Файл — `compose.yaml` /
  `docker-compose.yml` в корне (`subdir`, `compose_file` — если иначе).
- `vars` — значения для `${VAR}` в compose (не секреты). Всегда есть
  `STAND_URL` (`https://<name>.stand.yakutov.com`) и `STAND_NAME` — адрес
  сервиса для ссылок, напр. `vars: {BASE_URL: "https://stt-25.stand.yakutov.com",
  COOKIE_SECURE: "true"}`.
- `${VAR:?}` без значения (пароль БД) — stand подставит случайное и
  запомнит для пересборок.
- Наружу — один сервис: тот, у кого `ports`, иначе единственный с `build`;
  иначе укажи `service`. Порт — из `ports`/`expose` или `app_port`.
- Повторный `stand_up` сохраняет тома (данные БД), `stand_down` удаляет всё.
- Нельзя: bind-тома, `privileged`, `cap_add`, `network_mode`, `devices`,
  секции `networks`/`secrets`/`configs`. Ошибка называет ключ.

Команды внутри: `stand_exec` (`command` — argv, `service` — по умолчанию
открытый наружу), напр. `["pnpm", "create-lead-link", "--dept", "152"]`
или в БД `service: db`, `["psql", "-U", "app", "-c", "select 1"]`.
Логи сервиса — `stand_logs` с `service`.

## Проверить

Playwright MCP: открыть `https://<имя>.stand.yakutov.com`, пройти изменённый
сценарий, снять скриншот. Ждать `load`, не `networkidle`. Консоль —
`browser_console_messages`.

## Если упало

- `stand_status` — статус, причина, хвост лога сборки.
- `stand_logs` — логи работающего стенда (SSR-ошибки) или сборки.

Сборка упала на коде ветки (типы, импорты) — чинить в ветке и `stand_up`
снова. Упала на окружении (сеть, git01, «нет свободных портов», «уже 8
стендов») — это не твоя задача: опиши в отчёте и упомяни автора задачи.

## Артефакт без сборки

Отчёт, схема, прототип-страница: `art_publish` с абсолютным путём к `.jsx`/
`.tsx` (React, `export default`), `.html`, `.md`, `.mmd`, `.svg` или каталогу
с `index.html`. `art_list`, `art_rm` — список и удаление.

## Отчёт

В комментарий задачи: ссылку на стенд, ветку и коммит, что проверено и
скриншот. Стенд больше не нужен — `stand_down`. Чужие стенды не трогай.
